Перед генерацией загадок и диалогов прочитай `docs/domovata_style_guide.md`. Все тексты, которые пишет ИИ (riddle, dialogue_replica, choice_reason), должны соответствовать стилю Домовят.

ЭТАП 4: ЗАПОЛНЕНИЕ TASKS

ГЛОССАРИЙ ТЕРМИНОВ

Термин | Описание
--------|----------
HOG (Hidden Object Game) | Скрытый предмет, который игрок должен найти в игровом мире
Task type | Тип задания, определяющий механику игрового процесса
Classname | Уникальный идентификатор квеста или предмета в системе
GR (Game Resource) | Игровой ресурс, который выпадает при определенных действиях
Collection | Коллекционные предметы, которые игрок собирает
is_silhouette | Параметр, указывающий, что предмет показан только силуэтом
is_hide | Параметр, скрывающий иконку предмета под знаком "?"
Mystery | Особый тип задания в форме загадки
in_guest | Параметр, указывающий, что действие выполняется в гостях у друзей

PER (запрос) | [Тема]_[Год]_PER_[Номер] | Easter_2025_PER_1

Свободные подарки | [Тема]_[Год]_FG_[Номер] | Easter_2025_FG_1

Требования к этапу:
- Заполнить смысловые слоты для каждого таска в `task_choices.json`
- Выбрать кандидатов и generated-предметы по смыслу квеста
- Не писать вручную fixed-поля шаблонов, которые собирает код
- Соблюдать правила нейминга
- Для загадок (mystery) создавать рифмованные тексты

Ограничения:
1. Нельзя менять текст который не находится в [] в шаблонах это стандартный текст и должен остаться как есть.
2. ИИ не пишет `task_object` напрямую. ИИ пишет только выборы и смысловые поля в `task_choices.json`, затем код собирает строгий `filled_tasks.json`.

НОВЫЙ WORKFLOW ЭТАПА 4

Этап 4 теперь работает не напрямую с raw-данными и не с полным индексом.

Входные файлы:
- `campaigns/<campaign_id>/<pack_id>/context_pack.json` — основной вход для ИИ. В нем есть квесты, таски, выбранные `task_template_id`, контекст сюжета и компактные списки реальных кандидатов.
- `data/task_templates.json` — машинный каталог актуальных шаблонов `TT-001` ... `TT-035`.
- Для campaign workflow собирай `context_pack.json` быстрой командой `python src/workflow_fast.py context --campaign <campaign_id> --pack <pack_id>`.

Результат этапа 4:
- `campaigns/<campaign_id>/<pack_id>/task_choices.json` — пишет ИИ
- `campaigns/<campaign_id>/<pack_id>/filled_tasks.json` — собирает код
- `campaigns/<campaign_id>/<pack_id>/filled_tasks.validation.json` — пишет validator

После заполнения `task_choices.json` обязательно запустить сборку и проверку:

```bash
python src/workflow_fast.py fill --campaign <campaign_id> --pack <pack_id>
```

Если сборщик или валидатор нашел ошибки, нужно исправить `campaigns/<campaign_id>/<pack_id>/task_choices.json` или попросить ИИ перезаполнить конкретные task.

ГЛАВНОЕ ПРАВИЛО ЭТАПА 4

ИИ отвечает за смысл: какой кандидат выбран, какой generated-предмет нужен, какая загадка написана, почему выбор подходит к квесту.

Код отвечает за форму: `title`, `hint`, `classname`, `icon`, `action`, `search_action`, `after_buy_actions`, `go_to_location`, `identifier` и другие fixed-поля шаблона собираются автоматически по `data/task_templates.json` и строгой логике Stage 4.

ИИ не должен переписывать fixed-текст шаблонов красивой отсебятиной. Если в шаблоне написано `hint: "Попроси у друзей или купи."`, итоговый `filled_tasks.json` должен получить именно этот текст от кода.

Нельзя выдумывать:
- `garbage_classname`
- `garbage_title`
- `flower_classname`
- `flower_title`
- `collection_classname`
- `collection_title`
- реальные location title

Все эти значения должны быть взяты только из `candidates` внутри `campaigns/<campaign_id>/<pack_id>/context_pack.json`.

Если в `context_pack` есть note `Campaign memory excluded ...`, значит часть кандидатов уже использовалась в предыдущих pack этой campaign. Не пытайся вернуть их вручную: выбирай из свежих кандидатов, которые остались в списке.

Можно создавать по неймингу пакета:
- `GR`
- `ASK`
- `PER`
- `CL`
- `FA`
- `HOG`
- `R`
- `Character`
- `Stuff`
- action classname для dialog/give/craft/post_photo

СТРОГИЕ ПРАВИЛА РЕАЛЬНЫХ ЛОКАЦИЙ

Любая фраза в `hint`, которая указывает место, должна ссылаться только на существующую игровую локацию.

Строго проверяемые фразы:
- `Он находится ...`
- `Она находится ...`
- `Место поиска: ...`
- `Найди его у себя на ...`

Правило:
- После этих фраз нельзя писать сюжетные или атмосферные места.
- Нельзя писать: `у крыльца`, `под тучей`, `в мясном дожде`, `у котла`, `на небесной трещине`, если такой локации нет в `context_pack`.
- Нужно использовать точный `title` реальной локации из `candidate.locations`.
- Если у выбранного candidate несколько `locations`, в `Место поиска:` нужно перечислить все их `title` через запятую в том порядке, в котором они пришли в `context_pack`.
- Для мусора это особенно строго: если `candidate.locations` содержит `Озеро девичьих слез`, `Пещера`, `Темный лес`, `Трюм`, то hint должен писать `Место поиска: Озеро девичьих слез, Пещера, Темный лес, Трюм`, а не только одну локацию.

Примеры:

Плохо:
```json
"hint": "Поговори с Дедушкой Домоведом. Для этого просто кликни на него. Он находится у крыльца под фрикадельковой тучей."
```

Хорошо:
```json
"hint": "Поговори с Дедушкой Домоведом. Для этого просто кликни на него. Он находится в Барной комнате."
```

Плохо:
```json
"hint": "Найди Следы мясного дождя. Место поиска: крыльцо у дома. Если найти все не удаётся, можно купить подсказку."
```

Хорошо:
```json
"hint": "Найди Следы мясного дождя. Место поиска: Барная комната. Если найти все не удаётся, можно купить подсказку."
```

Если для generated/story template нет своего candidate, используй реальную локацию из других кандидатов этого же квеста в `context_pack`.
Если подходящей реальной локации нет, не выдумывай ее: нужно запросить новый context pack или ручной override.

ПРАВИЛО РАЗДЕЛЕНИЯ ИСТОЧНИКОВ

В одном квесте не нужно ставить:
- task на уборку конкретного мусора;
- и task на получение элемента коллекции, который выпадает из этого же мусора.

Плохо:
```text
TT-021 garbage FoxTrail
TT-011 collection_drop FoxTrailCollection5 из FoxTrail
```

Лучше:
```text
TT-021 garbage FoxTrail
TT-011 collection_drop из другого source_classname
```

Причина: игроку это выглядит как повтор одного и того же источника, а квест должен давать разнообразные действия.

ПРАВИЛО НУМЕРАЦИИ GENERATED-СУЩНОСТЕЙ

Нумерация generated-сущностей идет отдельными списками по типу сущности, а не по номеру task.

Для пакета `MeatballRain_2026` правильно:

```text
MeatballRain_2026_HOG_1
MeatballRain_2026_GR_1
MeatballRain_2026_ASK_1
MeatballRain_2026_GR_2
MeatballRain_2026_R_1
```

Неправильно:

```text
MeatballRain_2026_HOG_2
MeatballRain_2026_GR_6
MeatballRain_2026_ASK_7
MeatballRain_2026_GR_8
MeatballRain_2026_R_9
```

Отдельные счетчики:
- HOG: `[Префикс]_HOG_1`, `[Префикс]_HOG_2`, ...
- GR: `[Префикс]_GR_1`, `[Префикс]_GR_2`, ...
- ASK: `[Префикс]_ASK_1`, `[Префикс]_ASK_2`, ...
- PER: `[Префикс]_PER_1`, `[Префикс]_PER_2`, ...
- CL: `[Префикс]_CL_1`, `[Префикс]_CL_2`, ...
- FA: `[Префикс]_FA_1`, `[Префикс]_FA_2`, ...
- R: `[Префикс]_R_1`, `[Префикс]_R_2`, ...

Для `GR с цветов` тоже используй общий счетчик `GR`, если отдельная инструкция пакета не требует иначе.

ПРАВИЛО ВИЗУАЛИЗИРУЕМЫХ ПРЕДМЕТОВ

Generated-предметы `GR`, `ASK`, `PER`, `CL`, `FA`, `R` должны быть конкретными объектами, которые можно нарисовать и добавить в игру.

Нельзя делать предметом абстрактную сущность:
- `Небесное давление`
- `Магическая сила`
- `Сытость`
- `Заряд радости`
- `Фрикадельковый фронт`

Нужно делать предметом физический объект:
- `Латунная стрелка барометра`
- `Крышка для непослушного котла`
- `Лепесток сытости`
- `Соусный клапан`
- `Медный фиксатор трещины`

Если хочется передать абстрактную идею, привяжи ее к предмету:
- не `Небесное давление`, а `Латунная стрелка барометра`;
- не `Сытость`, а `Лепесток сытости`;
- не `Магия котла`, а `Закопченный амулет котла`.

ФОРМАТ `task_choices.json`

ИИ на этапе 4 отвечает не полным `task_object`, а смысловым JSON-объектом:

```json
{
  "quests": [
    {
      "classname_quests": "[classname квеста]",
      "tasks": [
        {
          "task_number": 1,
          "selected_candidate_id": "garbage:Ashes"
        },
        {
          "task_number": 2,
          "item_title": "Барабанные палочки"
        },
        {
          "task_number": 3,
          "item_title": "Парадный барабан"
        },
        {
          "task_number": 4,
          "selected_candidate_id": "garbage:Garbage_WarmBlanket",
          "riddle": "На кресле тихо я лежу, узором домик сторожу. У друга взглядом отыщи, и след в истории найди."
        }
      ]
    }
  ]
}
```

Обязательные поля quest-записи в `task_choices.json`:
- `classname_quests`
- `tasks`

Обязательные поля task-записи:
- `task_number`
- `selected_candidate_id`, если у task есть `candidates`
- `item_title`, если task создаёт generated-предмет (`HOG`, `ASK`, `PER`, `GR`, `R`, `FA`, `CL`)
- `riddle`, если task относится к mystery-шаблонам `TT-022` ... `TT-026`
- `dialogue_replica`, если task — диалог `TT-001`

ИИ не пишет `task_object`. После сохранения `task_choices.json` код создаёт:
- `filled_tasks.json`
- `filled_tasks.build.json`
- `filled_tasks.validation.json`
- `filled_tasks.preview.md`

Если шаблон не требует реального кандидата, например `TT-001`, `TT-002`, `TT-008`, `TT-009`, `TT-033`, `TT-034`, тогда `selected_candidate_id` не нужен. Для таких задач ИИ заполняет смысловые поля: `item_title`, `location_title`, `dialogue_replica`, `person`, `riddle`.
КАК ВЫБИРАТЬ КАНДИДАТА

Для каждого task в `context_pack.json` есть:
- `task_template_id`
- `task_template_name`
- `task_type`
- `description`
- `congratulation`
- `character`
- `candidate_domain`
- `candidates`
- `manual_override`
- `notes`

Правила выбора:
1. Выбери ровно один `selected_candidate_id` из `candidates`, если список `candidates` не пустой.
2. Не выбирай кандидата вне списка.
3. Если есть `manual_override.avoid_candidates`, не выбирай эти `candidate_id`.
4. Если есть `manual_override.prefer_candidates`, сначала попробуй выбрать из них, но только если это подходит контексту.
5. Если есть `manual_override.instruction`, выполни эту инструкцию.
6. Подбирай кандидата по смыслу `description`, `congratulation`, `title_quest` и персонажа.
7. Выбор должен быть формально осмысленным, а не атмосферным. Если в квесте речь о конкретных вещах вроде солений, огурцов, рассола, банки, соли, крышки, бочки или помидоров, сначала ищи кандидатов с прямой предметной связью: `collection_title`, `source_title`, `garbage_title`, `flower_title` или generated item должны поддерживать эту вещь по названию, материалу, функции или бытовой ассоциации.
8. Не выбирай кандидата только потому, что он "похож на улику", "поддерживает настроение" или "рифмуется", если предметная связь слабая.
9. Если в текущем `context_pack` нет осмысленного кандидата для конкретного контекста, не заполняй task слабым вариантом: нужно пересобрать `context_pack` с большим `--candidate-limit`, добавить manual override или попросить пользователя уточнить.
10. Если в одном квесте есть крафт (`TT-002`) или передача предмета (`TT-033`), то соседние generated-ресурсы `ASK`, `PER`, `GR` должны быть частью, ингредиентом или близкой по смыслу деталью итогового предмета. Не выбирай абстрактные ресурсы: название ресурса само должно показывать связь с итоговым предметом.
11. `TT-002` и `TT-033` считаются одной craft-like категорией и не должны стоять близко друг к другу: ориентир - один craft-like квест примерно на 4 квеста. В pack из 3 квестов допустим только один `TT-002` или `TT-033`.
11. Для `HOG clean_debris` игрок ищет конкретный скрытый объект. `title` должен быть действием с предметом/ресурсом/персонажем/зверем, а не абстрактным осмотром места.
12. Текст вне `[]` в подробных шаблонах обязателен. Нельзя переписывать фиксированные `title`, `hint`, `search_action`, `after_buy_actions` красивой отсебятиной.
13. Для mystery-задач `hint` должен быть рифмованной загадкой. Нельзя писать в `title` или `hint` ответ, слова из названия ответа или место поиска.

Как использовать кандидатов:

Для `candidate_domain = "garbage"`:
- код поставит `task_object.classname = candidate.garbage_classname`;
- для смыслового выбора смотри `candidate.garbage_title`; fixed `title/hint` соберет код;
- место поиска бери из `candidate.locations`;
- если у candidate несколько локаций, перечисляй все локации из `candidate.locations`, а не только первую.

Для `candidate_domain = "flower"`:
- код поставит `task_object.param = candidate.flower_classname`;
- для смыслового выбора смотри `candidate.flower_title`; fixed `title/hint` соберет код.

Для `candidate_domain = "collection_drop"`:
- код поставит `task_object.classname = candidate.collection_classname`;
- код поставит `icon = candidate.collection_classname`, если шаблон требует `icon`;
- для смыслового выбора смотри `candidate.collection_title`; fixed `title/hint` соберет код;
- источник выпадения бери из `candidate.source_title`, `candidate.source_type`, `candidate.mode`, `candidate.locations`.
- Для mystery collection (`TT-026`, `TT-027`) выбранный collection item должен подходить к контексту по прямой предметной логике. Не выбирай абстрактную или случайную коллекцию только ради рифмы.
- В тексте загадки нельзя писать название локации поиска и однокоренные слова от этой локации. Локация может быть указана только в обычном hint для не-mystery задач, где это требуется форматом.
- В mystery hint нельзя прямо называть искомый предмет или его очевидные однокоренные слова. Загадка должна описывать признаки предмета, но не подсказывать его названием.

Для `candidate_domain = "gr_garbage"`:
- код создаст `task_object.classname` и `icon` как `[Префикс]_GR_[Номер]`;
- в hint используй `candidate.garbage_title`;
- место поиска бери из `candidate.locations`;
- сам GR — новый ресурс пакета, но источник мусора должен быть реальным кандидатом.

Для generated/story templates без кандидатов:
- используй контекст квеста;
- соблюдай нейминг;
- не вставляй реальные garbage/flower/collection, если их нет в кандидате.

ТИПИЧНЫЙ ПОРЯДОК РАБОТЫ ИИ НА ЭТАПЕ 4

1. Открыть `campaigns/<campaign_id>/<pack_id>/context_pack.json`.
2. Для каждого квеста прочитать `title_quest`, `description`, `congratulation`, `Character`.
3. Для каждого task посмотреть `task_template_id`.
4. Найти соответствующий шаблон в этой инструкции.
5. Выбрать кандидата из `candidates`, если он нужен.
6. Заполнить смысловые поля в `task_choices.json`: `selected_candidate_id`, `item_title`, `location_title`, `riddle`, `dialogue_replica`.
7. Проверить, что выбранные реальные данные взяты только из `candidates`, а generated-предметы являются конкретными предметами.
8. Сохранить итоговый JSON в `campaigns/<campaign_id>/<pack_id>/task_choices.json`.
9. Запустить `python src/workflow_fast.py fill --campaign <campaign_id> --pack <pack_id>`.

КРИТИЧЕСКИЕ ОШИБКИ ЭТАПА 4

Нельзя:
- выбирать `selected_candidate_id`, которого нет в `context_pack`;
- менять `task_template_id` на этапе 4;
- использовать `TT-035`;
- придумывать реальные collection/garbage/flower classname;
- придумывать реальные локации в `hint`;
- писать после `Он находится` или `Место поиска:` локацию, которой нет в `context_pack`;
- писать только одну локацию в `Место поиска:`, если у выбранного candidate в `candidate.locations` есть несколько реальных локаций;
- использовать collection title от одного кандидата, а classname от другого;
- использовать garbage title от одного кандидата, а classname от другого;
- ставить в одном квесте уборку мусора и collection drop из того же самого мусора;
- для flower task ставить `param`, которого нет в выбранном flower candidate;
- нумеровать generated-сущности по номеру task вместо отдельного счетчика сущности;
- делать `GR`, `ASK`, `PER`, `R` абстрактными сущностями, которые нельзя отрисовать как предмет;
- выбирать кандидата с абстрактным или слабым обоснованием, когда квест требует конкретной предметной связи;
- писать в mystery-загадке название локации поиска, однокоренные слова от локации, название искомого предмета или очевидные однокоренные слова от предмета;
- игнорировать `manual_override`;
- возвращать CSV вместо `task_choices.json`;
- писать `task_object` вручную там, где его должен собрать код.
- маскировать близко стоящие `TT-002` и `TT-033` через Stage 4; такой план нужно исправлять на Stage 3.

ШАБЛОНЫ ДЛЯ РАЗНЫХ ТИПОВ ТАСКОВ:

Источник актуального списка: таблица `Шаблоны тасков.csv`.

ID шаблона таска — стабильный идентификатор шаблона для этапа 4. Русское название шаблона сохранено как в таблице.

Важно:
- `task_template_id` не является полем игрового task object. Это служебный ID инструкции.
- Все значения в квадратных скобках нужно заполнить по контексту квеста и реальным данным.
- Мусор, цветы, коллекции, локации и их title брать только из `data/quest_ready_index.json` и `data/quest_ready_drops.index.json`.
- Пакетные сущности квеста (`HOG`, `GR`, `ASK`, `PER`, `CL`, `FA`, `R`, `Character`, `Stuff`) создаются по правилам нейминга текущего квестового пакета.
- Поле `identifier` присутствует в актуальной таблице как пустое служебное поле. Если pipeline не требует его в JSON task object, оно может оставаться пустым.
- `amount` и `price` ИИ не подбирает вручную. Код берёт значения из `data/task_templates.json` (`task_object_defaults`), перенесённые из `Шаблоны тасков.csv`.
- Если нужен редкий ручной override, его можно явно указать в `task_choices.json`; без override используются средние значения шаблона.

TT-001. Диалог

Для `TT-001` на уровне task-записи обязательно добавь поле:

```json
"dialogue_replica": "[реплика персонажа]"
```

Правила:
- реплика пишется от лица персонажа, который указан в диалоговом task;
- длина `dialogue_replica` — не более 360 символов с пробелами;
- в `dialogue_replica` не добавляй префикс `РЕПЛИКА ДИАЛОГА:` — его добавит CSV exporter;
- в `hint` выбирай местоимения по полу персонажа: женский род `на неё. Она находится`, мужской род `на него. Он находится`;
- реплика не является полем `task_object`; она нужна для заголовочной строки CSV `Таск N;Диалог`.

Дополнение для campaign/pack workflow:

Этап 4 можно начинать после утвержденного этапа 3 и автоматически собранного context_pack. Отдельный апрув этапа 3.1 не нужен. После результата этапа 4 нужно остановиться, показать пользователю `task_choices`, собранные task objects и результат валидации. Нельзя запускать этап 5 без апрува пользователя.

Generated-объекты `HOG`, `GR`, `ASK`, `PER`, `CL`, `FA`, `R` нумеруются по всей campaign, а не внутри отдельного pack. Перед заполнением task choices смотри `context_pack.generated_sequence_offsets` и `context_pack.next_generated_numbers`.

Если первый pack уже использовал `MeatballRain_2026_HOG_1`, `MeatballRain_2026_GR_1`, `MeatballRain_2026_GR_2`, `MeatballRain_2026_ASK_1`, `MeatballRain_2026_R_1`, то следующий pack должен продолжать как `MeatballRain_2026_HOG_2`, `MeatballRain_2026_GR_3`, `MeatballRain_2026_ASK_2`, `MeatballRain_2026_R_2`.

Нельзя начинать нумерацию generated-объектов заново в pack 2 и нельзя добавлять `Pack2` в prefix classname, если это та же сюжетная campaign.
