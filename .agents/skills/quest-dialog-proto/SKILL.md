# Диалог и открывающий его экшен

Для каждого диалога создавай два отдельных JSON-файла с расширением `.proto.js`:

1. `UserInterfacePrototype` по образцу `server/prototypes/user_interface/dialog/Oseniny_2026/Oseniny_2026_Dialog_1.proto.js` — персонажи и реплики.
2. `QuestActionPrototype` по образцу `server/prototypes/quest_action/Oseniny_2026/Oseniny_2026_Character_2_Dialog_2.proto.js` — открывает этот UI через `show_user_interface`.

Краткие схемы обоих файлов находятся в [references/format.md](references/format.md). Не смешивай их структуру, ID и каталоги.

Каталоги по умолчанию: UI — `<game_repo_root>/server/prototypes/user_interface/dialog/<campaign_id>/`, экшен — `<game_repo_root>/server/prototypes/quest_action/<campaign_id>/`. Если пользователь указывает пути, используй их по назначению. Если указан только один каталог или `quest_action` назван каталогом UI-файла, уточни недостающий путь до записи.

## Входные данные

Дай пользователю [анкету](references/brief.md), когда сведений не хватает. Для UI нужны отдельный `id`, имя файла `.proto.js`, один или два персонажа с именами и точными `view_class` для базового состояния и используемых эмоций, а также реплики в нужном порядке. Для экшена нужны его `id`, имя файла `.proto.js`, путь и точная строка `conditions`. У каждого файла `identifier` выводи из его имени без `.proto.js`; оба ID должны различаться. Не придумывай classnames или `conditions`.

Строки вида `Дед (радость): «Текст»` — удобный пользовательский ввод: подпись определяет персонажа, метка в скобках определяет его эмоцию, содержимое `«...»` становится `text_tf` без внешних кавычек. Если завершающая точка стоит сразу после `»`, а внутри текста нет конечного знака, включи точку в `text_tf`: это часть пунктуации реплики. Число реплик равно числу таких строк; порядок сохраняй. Если персонажей двое, уточни их стороны; единственного персонажа располагай слева, если сторона не указана. Для каждого персонажа `speaker_tf` всегда равно одному заданному отображаемому имени, независимо от эмоции. Если эмоция молчащего персонажа не меняется явно, сохраняй его предыдущее состояние; исходное состояние — базовое, если пользователь не указал иное.

## Сборка

Подготовь структурированный UTF-8 JSON-бриф по полям из анкеты и запусти `py -3 .agents/skills/quest-dialog-proto/scripts/build_dialog.py <brief.json> --output-dir <каталог UI> --action-output-dir <каталог экшена>` (или `python`, если он доступен). Бриф может быть временным локальным файлом. Генератор проверяет оба набора данных до записи и пишет оба файла; существующие файлы перезаписываются только с `--force`. Если целевые каталоги недоступны для записи, сначала собери и проверь пару в локальном `output/`, затем перенеси каждый файл в согласованный каталог.

Сохраняй постоянную структуру образца: `class=UserInterfacePrototype`, `type=ui_dialog`, `processor=ui_template`, `params.view_class=Temp_Dialog_Window`, `offset={"x":0,"y":0}` и все переходы `dialog_effect_light_in`/`dialog_effect_light_out`. Каждый элемент `params.dialog` — один кадр и одна реплика. При одном персонаже включай только его `character_left` или `character_right`, без выдуманного второго персонажа. В каждом кадре каждого присутствующего персонажа пиши `"flip": "horizontal"`; пользователь при необходимости удалит это поле вручную позже. `speech_bubble.target_character` должен совпадать со стороной говорящего.

В экшене сохраняй `class=QuestActionPrototype`, `work_without_proof=1` и один `stuff_actions` с `do=show_user_interface`. Его вложенный `identifier` должен точно равняться `identifier` UI-файла; `conditions` записывай дословно из анкеты.

После генерации прочитай оба файла как JSON. Проверь оба `id` и `identifier`, число и порядок реплик, точные `view_class`, постоянное имя в `speaker_tf`, `flip`, отсутствие `????`, точную строку `conditions` и ссылку экшена на UI. Покажи пользователю пути к обоим файлам.
