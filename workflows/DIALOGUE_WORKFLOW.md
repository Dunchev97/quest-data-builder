# Подэтап 6.1 Подключение диалогов

Диалоги — обязательный завершающий подэтап обычного сюжетного quest pack. На творческих этапах 1–2 подготовить сцены и показать реплики пользователю. После ручной проверки основных XLSX Stage 6 подключить утверждённые сцены, назначить переданные пользователем ID и выполнить реальную конвертацию. Подэтап не запускает повторную генерацию Stage 6 и не меняет approval Stage 1–5.

По умолчанию один вступительный разговор становится первым таском первого квеста pack; по одному финальному разговору — последним таском каждого квеста. Если исходных сцен больше, объединить их и перенести события к этим точкам, сохранив причинную цепочку. Сценарный файл показывается для проверки до сборки proto. Для единичного диалога остаётся отдельный режим `quest-dialog-proto` без требования полного pack.

У основных quests/actions до подэтапа 6.1 должны быть назначены proto/task ID через существующую стадию `proto_ids.py`. Команда сохраняет эти значения и расходует новые диапазоны только на новые диалоги, экшены и разговорные таски.

Позиция таска не задаёт порядок выполнения: пользователь отказался от таких ограничений. В `QuestActionPrototype.conditions` только `active_quest=<quest_identifier>`. Не добавлять `accomplished_task`, проверки ресурсов, завершения соседних тасков или одноразовые флаги. Разговор засчитывается как `type=action`, `amount=1`. После него квест завершается, когда выполнены остальные таски.

## Источники данных

- `campaigns/<campaign_id>/dialogue_characters.json` — игровые `classname`, графические `view_class`, отображаемые имена, доступные эмоции, фактические направления ассетов `asset_facing`, локация и готовый текст `talk_title` в нужном падеже.
- `campaigns/<campaign_id>/<pack_id>/dialogue_plan.json` — утверждённые реплики, стороны, эмоции, цель клика, quest и позиция каждого разговора. Это постоянный машинный источник, а не дополнительный отчёт поставки.
- Текущие ручные `<campaign_id>_quests.xlsx` и `<campaign_id>_actions.xlsx`, по одному листу `conf`. Перед повторным запуском читать их заново. Для VelesNight_2026 рабочая папка пользователя имеет приоритет над `review/proto/`.
- Реальные доноры, уже существующие proto и настоящий игровой конвертер в указанном `--game-root`.

Спрашивать только недостающее. Не придумывать графические классы, эмоции, размещение объектов и свободные ID. Стороны, эмоции из доступных и участника для клика можно выбирать по смыслу, когда пользователь оставил это ИИ. Имя локации нужно для подсказок; расстановка объектов и координаты не добавляются автоматически этим подэтапом.

Перед сборкой спросить, куда без `flip` фактически смотрит каждый используемый графический ассет, включая эмоции. Можно одним ответом подтвердить одинаковое направление всех эмоций; не выводить его из названия класса. Сохранять ответ в реестре по точному `view_class` и повторно использовать. При отсутствии направления используемого ассета генератор останавливается, чтобы ИИ запросил недостающее значение.

## Реестр персонажей

```json
{
  "version": 1,
  "location": "Тёплые истории",
  "characters": {
    "ded": {
      "name": "Дед Домовед",
      "classname": "Example_2026_Character_1_1",
      "view_class": "Oseniny_2026_Character_1",
      "emotions": {"радость": "Oseniny_2026_Character_1_Happy"},
      "asset_facing": {
        "Oseniny_2026_Character_1": "left",
        "Oseniny_2026_Character_1_Happy": "left"
      },
      "talk_title": "Поговори с Дедом Домоведом"
    }
  }
}
```

Ключ `ded` связывает персонажа с планом и может быть другим стабильным идентификатором. `location` можно задать отдельно у персонажа. Базовая эмоция автоматически получает его `view_class`; дополнительные классы перечисляются в `emotions`. Не строить их имена добавлением предполагаемых суффиксов.

`helper` квеста — графический класс. ИИ не должен подставлять туда автоматически созданный furniture classname. `icon`, `go_to_location`, физическая цель клика и запись в `behaviour` используют игровой `classname`. Stage 6 сразу преобразует `helper`, если реестр уже существует; подэтап 6.1 проверяет и адресно обновляет его в текущем XLSX. Для неоднозначного helper в плане задать `quest_helpers: {"<quest_identifier>": "<character_key>"}`.

## План диалогов

Каждый элемент `dialogs` содержит следующие поля:

| Поле | Значение |
|---|---|
| `quest` | Точный identifier квеста из текущего XLSX |
| `position` | `start` для единственного вступления или `end` |
| `target` | Ключ персонажа, по которому нужно кликнуть |
| `characters` | Один или два объекта `{"key":"ded","side":"left"}`; у двух персонажей стороны разные |
| `lines` | Реплики вида `{"speaker":"ded","emotion":"базовая","text":"Спасибо, домовёнок!"}` |
| `file_name` | Необязательное точное имя UI `.proto.js`; при отсутствии генерируется с campaign и pack |
| `action.file_name` | Необязательное точное имя экшена `.proto.js` |
| `id`, `action.id`, `task_identifier` | Существующие назначенные ID сохраняются; у новых элементов поля можно пропустить |
| `task.title`, `task.hint` | Необязательные тексты нового таска; иначе берутся `talk_title` и локация |

Корень JSON: `version=1`, `campaign_id`, `pack_id`, `dialogs`. Вступление и завершение первого квеста — разные элементы. В `lines` поддерживается `other_emotions` по контракту отдельного генератора. Каждый кадр содержит одну реплику; состояние молчащего персонажа сохраняется. Персонаж слева должен смотреть вправо, справа — влево: `flip="horizontal"` добавляется только если исходный ассет смотрит наружу, то есть его `asset_facing` совпадает со стороной в окне. В остальных случаях поле отсутствует. Правило применяется по текущему `view_class` в каждом кадре.

Имена файлов после первой сборки и ID записываются обратно в план. Имена уже созданных файлов и назначенные ID не менять при повторном запуске. Если существующий proto отличается от утверждённого плана, команда останавливается: сначала сверить ручной файл с планом и согласовать актуальную редакцию.

## Команда

```powershell
python src/workflow_fast.py dialogs --campaign <campaign_id> --pack <pack_id> --game-root <game_repo_root> --tables-dir <актуальные_XLSX> --proto-start <первый_свободный_proto_ID> --task-start <eID>
```

По умолчанию создаётся проверяемый кандидат в `output/`, без изменения рабочих XLSX и игровых proto. Добавить `--apply` для записи проверенного результата. Если применение уже поручено пользователем, ИИ может выполнить эту команду сразу; отдельного повторного разрешения на запись не требуется.

`--characters` и `--plan` переопределяют входные JSON, `--node` задаёт Node executable, `--output-dir` — пустую папку кандидата. Без `--tables-dir` команда предпочитает существующую `<game_repo_root>/data_ingenering/GD/Quests_Story/<campaign_id>/`, иначе `review/proto/` pack. Для новых ID нужны явно переданные стартовые значения. Для проверки уже полностью подключённого pack диапазоны повторно сообщать не нужно.

## Что делает команда

1. Проверяет полноту плана, персонажей, локации и текущих таблиц. Собирает занятые ID из всех XLSX папки, включая простые формулы последовательных ID, не меняя эти файлы. Занятые значения пропускает.
2. Через существующий `build_dialog.py` создаёт UI/экшен для каждой сцены. Таски добавляет адресно: существующие поля, ID, формулы, комментарии, стили и объединения сохраняет; номера `tasks.N` сдвигает при вставке вступления. Формулы с адресными ссылками, которые нельзя безопасно сдвинуть, требуют отдельной сверки.
3. Добавляет экшены в `stuff_action` персонажей и в их текущие блоки `actions.xlsx`, сохраняя прежние действия и остальные behaviours. Различает root `behaviour` и существующий `behaviour.0.actions`. Не создаёт выдуманных персонажей.
4. Назначает новые task ID через `proto_ids.assign`, сохраняет старые и проверяет уникальность. Повторный запуск распознаёт разговор по `action`: не дублирует таски, экшены и ID. Ручные title/hint существующего таска сохраняет.
5. Запускает `validate_proto_exports.py` в изолированной папке с `--assigned-ids`, проверяя обновлённые quests/actions и сохранение всех заданных полей. Для всего pack остаются обязательными общие проверки ресурсов, рецептов и технической очистки по `PROTO_EXPORT_WORKFLOW.md`; успешная проверка этих двух таблиц не заменяет их.
6. При `--apply` сохраняет резервные копии в `output/`, проверяет блокировки и отсутствие параллельных правок, записывает таблицы, новые UI/actions и соответствующие task/helper/behaviour в игровых proto. При ошибке записи откатывает уже записанные файлы. Копии в другой рабочей папке автоматически не синхронизирует.

На выходе сообщить количество диалогов и новых/существующих тасков, проверку конвертером, фактические и следующие свободные ID, пути к таблицам/proto и резервным копиям. Сам магазин, станок и ручную расстановку персонажей не менять. UI и actions — служебные определения; добавлять их в `remove_asset`/`remove_stuff` не нужно.
