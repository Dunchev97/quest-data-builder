# XLSX для реального конвертера прототипов

Этот контракт обязателен для Stage 6 и FunCollection. Скилл `.agents/skills/proto/SKILL.md` и его validator используют те же проверки, что `src/converter_tables.py`.

## Файлы и ручные правки

### GR: текст обязан совпадать с реальным выпадением (21.10.2026)

Каталог `data/task_templates.json` различает TT-013 (мусор в локации дома), TT-014 (конкретный мусор в гостях), TT-015 (конкретный мусор дома). Выбранный `garbage_classname` означает конкретный источник: Stage 4 преобразует старый TT-013 в TT-014/TT-015 по mode кандидата, выводит фактические имя/id/type и сохраняет requested_task_template_id для прослеживаемости. Баланс берётся из фактического шаблона, явно заданные amount/price choices сохраняются. Это единственная разрешённая нормализация этого расхождения; произвольные несовпадения шаблонов с контекстом по-прежнему запрещены. Шаблон с конкретным мусором и кандидат с противоположным mode — ошибка.

Единый formatter `src/gr_sources.py` формирует hint задачи и description GR из названия **мусора-источника**, режима и полного списка локаций. Например, для RustyNail и clean_garbage_in_guest: `Убирай Ржавый гвоздь в гостях, чтобы найти. Место поиска: Котельная.` Название GR («Железные крючки») не является названием мусора. Не добавлять общее слово «мусор» перед конкретным названием. Ресурсный builder не копирует устаревший hint поверх известной механики. TT-013 без конкретных assets обязан иметь явные location_tags; иначе выпадение не ограничено обещанной локацией и сборка запрещена.

После ручных изменений источником механики служат `actions`, `assets`, `location_tags` **актуального resources.xlsx**, а не старый task_template_name и не текст подсказки. `src/gr_table_review.py` сопоставляет их с quest-ready индексом и текстами двух XLSX. Проверка встроена в Stage 6 и `validate_proto_exports.py` при проверке пары quests/resources. Для VelesNight_2026 исправлены подписи шаблонов, опечатка «Ржавый гроздь» и домашний режим Стружки при фактическом выпадении в гостях; источники, вероятности, количества и назначенные ID сохранены. Старые репозиторные копии не заменяют актуальную рабочую папку.

```powershell
python src/gr_table_review.py VelesNight_2026 --tables-dir D:/domovoy/trunk/data_ingenering/GD/Quests_Story/VelesNight_2026
python src/gr_table_review.py VelesNight_2026 --tables-dir D:/domovoy/trunk/data_ingenering/GD/Quests_Story/VelesNight_2026 --apply
```

По умолчанию команда ничего не пишет и возвращает ошибку при расхождении. `--apply` исправляет только hint/description и служебные названия шаблонов в существующих ручных XLSX. Обязательны предварительная проверка блокировок, резервные копии в output, сохранение всех прочих ячеек/ID/identifier/формул/стилей/закреплений и повторная проверка. Регенерация XLSX и изменение drop mechanics не разрешены этим ключом. Не применять старый Stage 4 поверх более поздних ручных mode/источников без их согласования.

**Рабочая папка пользователя для VelesNight_2026**, подтверждена 20.10.2026: `D:/domovoy/trunk/data_ingenering/GD/Quests_Story/VelesNight_2026/`. Пользователь вручную редактирует таблицы там и синхронизирует копии в `campaigns/VelesNight_2026/pack_001/review/proto/`. Проверять актуальную рабочую версию и сравнивать содержимое копий. Если репозиторий содержит старый файл, сначала учитывать эту рабочую папку; не предполагать сразу несохранённые правки Excel. Не заменять ручной эталон регенерацией и не синхронизировать поверх более новой версии автоматически. Обычная папка конечного экспорта генератора остаётся `review/proto/`.

Правило пользователя от 19.10.2026: **не закреплять строки в Excel-таблицах**. Оно действует для всех XLSX проекта. Старые требования закрепления на A4/A22/A76 отменены. Фиксация этого правила сама по себе не поручает пересохранять существующие ручные XLSX.

С 20.10.2026 правило также внедрено в генераторы: `src/export_xlsx.py`, дополнительные Adventure/report/TwoDays шаблоны и legacy split создают новые листы без закрепления (`freeze_panes=None`). Split не наследует freeze panes исходного master, при этом master остаётся неизменным. Проверка Stage 6 сверяет отсутствие закрепления у всех новых XLSX, включая ресурсы и Story_RandomRecipe. Адресное изменение ID или отдельных ячеек существующего ручного файла сохраняет его остальные настройки; само правило генерации не разрешает массовое пересохранение ручных таблиц.

Конечная выдача — XLSX и два обязательных TXT: список package для магазина и дополнение к станку (добавлены пользователем 20–21.10.2026), все в `campaigns/<campaign_id>/<pack_id>/review/proto/`. В каждом XLSX ровно один лист `conf`. Имя каждого конечного XLSX обязательно содержит точный campaign prefix. Обычно это `<campaign_id>_<тип>.xlsx`; уже содержащий prefix файл `quest_<campaign_id>_accomplished.xlsx` повторно не префиксовать.

- `quest_<campaign_id>_accomplished.xlsx`;

- `<campaign_id>_funcollection_4.xlsx`, если выбран этот объект потех. Он остаётся отдельной механикой, не ингредиентом quest craft.
- `<campaign_id>_shop_invisible_packages.txt` со всеми package из текущих XLSX.
- `<campaign_id>_DayOfDomovoyCaldron.txt` с дополнением ко всем рецептам станка.
- `MB_RECIPEMB_POTS_<campaign_id>.xlsx`: обязательные мистери-боксы, рецепты и горшочки.

## Обязательные мистери-боксы и горшочки: 20.10.2026

Для каждого quest pack всегда создавать `MB_RECIPEMB_POTS_<campaign_id>.xlsx`, ровно один лист `conf`. Образец структуры и связи наград — актуальный `MB_RECIPEMB_POTS_VelesNight_2026.xlsx` в рабочей папке пользователя, а не устаревшие source JSON. В файле 9 прототипов:

- 3 `<campaign_id>_R_MB_N`, donors `/mystery_box/Night_2026/Night_2026_R_MB_N.proto.js` (каждый N имеет свой состав donor-наград);
- 3 `<campaign_id>_R_MB_N_Recipe`, donor `/recipe/Night_2026/Night_2026_R_MB_1_Recipe.proto.js`;
- 3 `<campaign_id>_Pot_Multi_Magic_N`, donor `/pot/Night_2026/Night_2026_Pot_Multi_Magic_1.proto.js`.

**Для всех MB-рецептов ingredients дословно равен ingredients первого `<campaign_id>_R_1_Recipe` в текущих XLSX.** Сохранять порядок, classname и количества. Номер N не означает источник R_N: R_MB_1/2/3 используют один и тот же R_1. При отсутствии/пустоте/неоднозначности первого рецепта останавливать сборку, не сочинять ресурсы. Полная проверка настоящим конвертером также сверяет это равенство.

Title допускает тестовые названия, которые пользователь заменит вручную. Сохранять donor mechanics и прочие награды, менять Night_2026 на текущую campaign во всех вложенных ссылках. Бокс N выдаёт горшочек N, recipe N создаёт box N; переносить только classname верхнего уровня недостаточно. Каждый MB — отдельный ml, каждый recipe/pot с replace — отдельный sl. Числа position=1, lifespan=3600, price=35 сохраняются из образца; id при первичной генерации пустые, формулы не создавать. Закрепления строк нет. В conditions по умолчанию `accomplished_or_restarted_group=<campaign_id>_Story`; временное ограничение добавлять только из подтверждённых настроек пользователя, донорскую дату не наследовать.

Генератор `src/mystery_rewards.py` встроен в Stage 6 после ресурсов/интерактивов и до технической таблицы. Уже существующий ручной файл сохраняется; он должен пройти сверку ingredients. MB — временные ресурсы для remove_asset. Наградные pot сохраняются у игрока и не попадают в очистку события. Это отдельная наградная таблица, не FunCollection-механика и не отдельный бокс на каждый Story_N.

```powershell
python src/mystery_rewards.py <campaign_id> --tables-dir <папка текущих XLSX>
python src/mystery_rewards.py VelesNight_2026 --tables-dir D:/domovoy/trunk/data_ingenering/GD/Quests_Story/VelesNight_2026 --update-ingredients
```

`--update-ingredients` меняет только ячейки ingredients всех R_MB_N_Recipe в существующем ручном файле (в образце три, дополнительные вручную добавленные N тоже учитываются), сохраняет title/id/формулы и остальные значения, делает обратимую копию в output и проверяет повторным чтением. Эта адресная операция не является подтверждением пригодности остальных ручных ячеек для конвертации: например, multi-input ml и формулы ID старого образца требуют отдельного converter review. При будущей первичной генерации эти ошибки не воспроизводить. Намеренная регенерация требует `--force` и предварительного учёта ручных правок.

Генератор `src/package_list.py` читает актуальные листы `conf` всех XLSX выбранной папки. Включаются только определения с output `/asset_package/...`; приоритет у явно заданного `classname`, иначе basename output. ## Папка прототипов квестов: исправление 20.10.2026

Все квесты campaign размещаются непосредственно в `/quest/event/<campaign_id>/`, без отдельных папок для `story_1`, `story_2` и без подкаталога `tech`:

- `/quest/event/VelesNight_2026/VelesNight_2026_Story_1.proto.js`;
- `/quest/event/VelesNight_2026/VelesNight_2026_Story_2.proto.js`;
- `/quest/event/VelesNight_2026/VelesNight_2026_Tech_1.proto.js`.

Группы также лежат в папке campaign: `/quest_group/event/<campaign_id>/<campaign_id>_Story.proto.js` и `/quest_group/event/<campaign_id>/<campaign_id>_Tech.proto.js`. Эти пути прочитаны из сохранённых ручных `VelesNight_2026_quests.xlsx` и `VelesNight_2026_technical_quests.xlsx`; 20.10.2026 копии в рабочей папке игры и `review/proto` совпали побайтово.

Donor `input` сохраняет реальный путь Night_2026. В каждом task-блоке `input` и `output` оба равны новому пути текущего квеста: старые ссылки в task-блоках не являются допустимым исключением. Несовпадение B/C проверяется validator; ссылка task на отсутствующий output дополнительно ловится полной проверкой назначенных IDs/реальным конвертером. Правило исправлено в генераторах quest group, сюжетных/технических квестов и старом helper `fill_tasks.make_proto_path`, проверяется regression tests. Текущие XLSX не регенерировать и не переназначать IDs ради смены папки.

## Назначение предоставленных пользователем ID

```powershell
python .agents/skills/proto/scripts/validate_converter_table.py <file.xlsx> --assigned-ids
```

- Один proto id на уникальный output path во всей поставке. Одинаковое имя файла в разных семействах (quest_item/global_reward) — разные прототипы. Повторное обновление одного прототипа, в том числе task-блок, не расходует новый proto id.
- Один уникальный task id на `(quest output, tasks.N)`; включать сюжетные и технические задачи. Существующие назначенные значения сохраняются; противоречия и коллизии останавливают операцию.
- Proto ID сохранять числом Excel, task identifier — строкой `e...`. Не заполнять id в array continuation-строках.
- Перед записью сохранить обратимую копию и проверить новый комплект в игнорируемом `output/`, проверить блокировки файлов. Никаких новых manifest/report JSON или копий в папке поставки. Повтор с теми же стартами не меняет существующие ID и не пересохраняет неизменённые файлы.
- Для проверки назначенной поставки добавить `--assigned-ids` к `validate_proto_exports.py` и передать все XLSX. Этот режим требует полноту, корректный тип и глобальную уникальность proto/task ID, затем проверяет их в JSON после настоящего конвертера, включая отсутствие лишних donor tasks. Авторский режим с пустыми ID остаётся отдельным строгим режимом.
- После назначения сообщить занятые диапазоны и следующие свободные номера. Для другой операции использовать актуальные стартовые значения пользователя: локальная запись не является глобальным резервированием IDs в игровом репозитории.

## Техническая группа и очистка события

Генератор `src/technical_quest_tables.py` создаёт `<campaign_id>_technical_quests.xlsx` в общей папке `review/proto`, ровно один `conf`. Stage 6 запускает его после quest/resource/action/interactive/FunCollection таблиц, чтобы очистка учитывала весь состав. Добавить отсутствующую таблицу к уже проверяемому pack можно отдельно, без пересборки существующих файлов:

```powershell
python src/technical_quest_tables.py <campaign_id> --pack <pack_id>
```

Проверенные доноры:

- `/quest_group/event/Night_2026/Night_2026_Tech.proto.js`;
- `/quest/event/Night_2026/Night_2026_Tech_1.proto.js`;
- `/quest/event/Night_2026/Night_2026_Tech_2.proto.js`.

Техническая группа скрыта по донору; Tech_1 автоматически стартует при активной `<campaign_id>_Story`, выполняет `have_location` с `location_index=1` и открывает Tech_2. Tech_2 содержит незавершаемую задачу `action=no_such_action`, `amount=1`; его `on_spoil` очищает сущности события. Служебные flags сохраняются из доноров через `replace Night_2026 → <campaign_id>`. `id` и identifier обеих задач пустые.

`spoil_conditions` группы всегда вынесен в явное поле для срока события (`time>YYYY-MM-DD HH:MM`). Если пользователь не задал срок, поле пустое и отмечено жёлтым с комментарием: его обязательно заполнить до импорта. Пустое значение не очищает донорскую дату; проверка конвертера не подтверждает готовность расписания. Нельзя молча переносить дату `2026-03-05 23:59` в новую campaign или придумывать дату события.

Состав `on_spoil` снимается с **текущих конечных XLSX всех pack этой campaign**, включая ручные переименования classname, все эмоции персонажей, Home/Guest пары, HOG, состояния и эффекты FunCollection. Старые технические таблицы и `~$*` пропускаются. Список строится по определениям прототипов, не по упоминаниям ингредиентов: общие игровые предметы из заданий удалять нельзя.

- `quest_item`, `workbench_item`, `mystery_box` → `{"do":"remove_asset","classname":"..."}`;
- `furniture`, `debris`, `chest`, `workbench` → `{"do":"remove_stuff","classname":"..."}`;
- перед удалением отменяется крафт стандартных story recipes на `DayOfDomovoyCaldron`, с `recipe_tags=["<campaign_id>"]`; свои workbench также включаются;
- `asset_package`, `recipe`, `global_reward`, quest/action/group/UI/post/friend-action — определения механик, а не удаляемые предметы; их не помещать в remove_asset/remove_stuff;
- classname обязан принадлежать campaign; дубликаты удаляются. Неизвестное семейство — ошибка, требующая явной классификации.

`on_spoil` — `ml` + `array`: одна JSON-запись на строку, последующие B/C пустые. В JSON-объектах удаления ключ именно `classname`, как в реальном доноре. Нельзя сохранять весь JSON-массив в одной ячейке или ограничиваться donor-списком Night_2026. `validate_proto_exports.py` при наличии технической таблицы сверяет полноту очистки с переданными XLSX и ловит пропущенные/переименованные сущности. Передавать на проверку весь комплект. После изменения состава сущностей пользовательская техническая таблица также требует актуализации и повторной проверки; `--force` применяется только при намеренной регенерации с учётом ручных правок.

## Как закрепляем ручные исправления

1. Пользователь проверяет и правит конечные XLSX, затем сообщает о завершении.
2. ИИ читает актуальные XLSX как ручной эталон, определяет исправленные поля и причины ошибок.
3. Подтверждённые исправления переносит в генераторы/шаблоны и нужный раздел документации. Нужные проверки добавляет для реальных случаев, без лишних отчётных файлов.
4. Проверяет эталон конвертером; отдельно проверяет, что исправленный код воспроизводит нужное поведение в тестовом `output/`. Эталон при этом не перезаписывает.
5. После завершения проверки таблиц оформляет скилл создания квестов по проверенному процессу. До этого этапа процесс считается постепенно полируемым, не окончательным.

Approval Stage 6 относится ко всем XLSX в папке: контрольная сумма рассчитывается по именам и содержимому таблиц, без отдельного manifest. Служебные Excel-файлы `~$*` не учитываются.

## Ошибки, которые нельзя повторять

1. Реальный `xlsx-to-json.js` принимает только `sl` и `ml`. `temp_01`/`temp_02` — названия JS-модулей, не директивы. Поддерживаемые типы: `string`, `int`, `array`, `object`, `ignore`, `replace`. Типов `array_of_values` и `array_of_objects` в проверенной версии нет.
2. `ml` создаёт ровно один прототип. Для каждого персонажа нужен свой блок. Продолжения `behaviour.0.actions` идут ниже в том же блоке, с пустыми B/C и без нового ID.
3. `sl` с `replace` также требует отдельного блока на каждый прототип: конвертер сбрасывает массив замен после первой записи. Иначе первая строка исправляется, остальные сохраняют donor references. Обычные `sl` без замен могут содержать много строк.
4. Для `object` объединять две клетки и в строке типов, и в строке ключей. Для `replace` объединять только строку типов, а ниже оставлять два заголовка `find` / `replace`. CSV эту структуру не сохраняет.
5. Пустые клетки должны быть настоящими `None`, а не сохранёнными inline string `""` или формулами `=""`. Иначе `sl` может читать ложную следующую строку и завершаться `EISDIR`.
6. `int` означает числовую клетку Excel. Цены/количества не писать текстом. `extra.open_now_btn_window` — `string`, потому что содержит текст кнопки и `{price}`.
7. При проходе через массив всегда указывать индекс. Для Exchanger верные ключи — `behaviour.0.window_spec.title_mark_workbencg`, `.ingredient_description`, `.description_1`, `.description_2`. Запись `behaviour.description_1` в JS может пройти без ошибки, но исчезнет при JSON serialization.
8. Exchanger обязан заменять `Fun10` на campaign prefix во всех вложенных ссылках: генераторы, пять RG, recipe, window, conditions, tags. HOG search обязан заменять donor target в каждом отдельном action. ASK/PER должны менять `tags.0` на campaign prefix.
9. Реальный donor quest group расположен в `/quest_group/event/Night_2026/Night_2026_Story.proto.js`. Старый donor-путь без директории `Night_2026` не существует в проверенном checkout. Generated output — `/quest_group/event/<campaign_id>/<campaign_id>_Story.proto.js`; Tech group хранится рядом как `<campaign_id>_Tech.proto.js`.
10. Повторяющиеся update keys запрещены. Единственное исключение — предусмотренные шаблоном Story_RandomRecipe две полностью пустые колонки `id`: null updates пропускаются конвертером. У FunCollection_4 popup — `extra.pop_up_message`, текст окна — `extra.description_window`. В HELP текст кнопки — `extra.window_spec.start_btn_title`; он не должен второй раз записываться в `comment_4`.
11. Ячейка типа `array` содержит один элемент; JSON-массив в ней превратится в вложенный массив. В `ml` элементы располагаются по вертикали; в `sl` горизонтальный диапазон массива объединяется в строке типа.
12. Формулы в поставке материализовать. Конвертер читает `cell.v`, а не вычисляет формулы. После сохранения заново открыть XLSX и проверить кириллицу, типы и объединения.
13. Пустой `id` **не удаляет ID донора**: `proto.recreate` пропускает null updates. Пустые клетки сохранять по контракту автора таблицы; разработчик назначает производственные IDs отдельным шагом перед импортом. Успешная конвертация не означает готовность всех скопированных IDs к загрузке в игру.

## FunCollection_4 с пользовательским classname

Источник структуры — `docs/FunCollection/FunCollection_4.xlsx`, только `conf`; машинный шаблон — `data/fun_interactive_object_templates.json#FunCollection_4`. Генератор — `src/fun_collection_tables.py`.

Для VelesNight_2026 сохранены `VelesNight_2026_INVITE`, `_Real`, `_Fake`. GR и десять CL остаются семейством `VelesNight_2026_FunCollection_4_*`. В state-блоках замены выполняются в порядке: GR → CL → базовое имя состояния → общий prefix. Иначе замена базового имени ошибочно превращает ресурсы в `INVITE_GR/CL`.

Негативные эффекты заменяют ссылки на состояния и оба встречающихся donor prefix `Fun12` / `Fun10`. Вложенные переходы должны вести к `INVITE`, а не к старому или выдуманному FunCollection classname.

По указанию пользователя VelesNight_2026 параметры места и техквеста он заполнит вручную. В таблице они существуют и отмечены жёлтым с комментариями: `location_tags`, `conditions`, `replace` для ID локации. ID 398 сохранён из реального донора. Имя `VelesNight_2026_Tech_Weekly_4` — заготовка по образцу донора, а не подтверждение существования такого прототипа. После ручных правок повторить validation и dry run.

## Проверка настоящим конвертером

Сначала найти актуальный checkout игры и прочитать `xlsx-to-json.js`, `myXLSX.js`, `object/getObject.js`, `proto.js`. Не прописывать путь чужой машины в генераторе.

Проверка копирует реальные доноры в новую изолированную папку, вызывает неизменённый игровой скрипт и блокирует записи за пределами этой папки.
